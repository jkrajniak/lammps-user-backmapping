## Context

`molecules[].source` (the AT fragment: a single-molecule atomistic reference used to place AT atoms relative to each CG bead) is currently GROMACS-only (`.gro` coordinates + `.top` topology), parsed by `parsers/gro_parser.py`/`parsers/top_parser.py`. `lammps-native-cg-input` (archived) added `cg_system.format: lammps`, explicitly deferring AT fragments on the assumption that AT-fragment bead-mapping's name-keyed atom references would need a new identity-mapping sidecar.

That assumption was too cautious. `builder.py` uses `atom.name` purely as an opaque lookup key throughout (`builder.py:322,343,457,564,745,813` etc.) — it splits `atoms:` entries on `:` and only ever uses the last segment (`parts[-1]`), never requiring it to be a symbolic name. The CG-side change already established the pattern for this: `cg_system.format: lammps` uses the LAMMPS numeric type ID (as a string) in place of a symbolic CG bead type name, with no sidecar. The same trick applies at the atom level for AT fragments: `atoms: ["1:DOD:1", "1:DOD:2"]` (numeric LAMMPS atom IDs) instead of `["1:DOD:C1", "1:DOD:C2"]`.

Where AT fragments genuinely differ from the CG side: `cg_mol.bonds`/`.angles` turned out to be dead code in `builder.py` (CG-CG bonded terms come entirely from `cross_interactions`), but `at_mol.bonds`/`.angles`/`.dihedrals` are actively read (`builder.py:340-620,776-940`) to build the real intra-bead bond/angle/dihedral coefficients, and `at_top.atom_types[...].sigma/epsilon` drive AT-AT pair coefficients (`builder.py:273-275`). So this change needs both a `data`-file connectivity reader (unlike the CG reader, which explicitly skips `Bonds`/`Angles`) and a genuine, if narrowly bounded, force-field-coefficient reader — the input-script parser the CG-side design.md scoped out and didn't end up needing.

Tracing exactly what's consumed narrows that reader considerably:
- Bonds: only `func == 1` (harmonic) intra-bead bonds are processed (`builder.py:345`); non-harmonic funcs are silently skipped even on the GROMACS path.
- Angles: same — only harmonic (`builder.py:462`).
- Dihedrals: only `func == 3` (Ryckaert–Bellemans) intra-bead dihedrals are processed (`builder.py:580: if func != 3: continue`), converted via `units.gromacs_rb_to_lammps` into the package's own native `dihedral_style ryckaert` (`writers.py:200`). A LAMMPS-native fragment can supply `dihedral_coeff` values in that native form directly — no RB→LAMMPS conversion math, and no GROMACS wildcard atom-type-pattern dihedral-type lookup (`resolve_dihedral_params`/`_lookup_dihedraltype`) is needed, since a LAMMPS `data` file's `Dihedrals` section already gives explicit atom quartets with explicit numeric type IDs.
- Pair: only per-type self (`i == i`) LJ sigma/epsilon are read from the topology (`builder.py:273-275`); cross-type (`i != j`) LJ parameters are always computed in Python via arithmetic/geometric mixing (`builder.py:634-636`), never read from the source file. So the reader only needs diagonal `pair_coeff i i` entries.

An existing file in `examples/dodecane/` already has exactly this bounded shape: `in.dodecane_at` (`units real`, `bond_style harmonic` + `bond_coeff`, `angle_style harmonic` + `angle_coeff`, `pair_style lj/cut` + `pair_coeff`), paired with `extract_at_frame.py`, which extracts a standalone AT-only `data` file (atoms, bonds, angles — with correct type IDs) from a backmapped hybrid output.

> **IMPORTANT CORRECTION (found during implementation, building the PE example):** the paragraph above draws a false parallel to the CG-side verification example. For CG, extracting from a built hybrid was correct because CG atom positions *are* the real, per-instance absolute positions — there is no template concept. AT fragments are different: `builder.py` places AT atoms via `dx = at_distance(at_gro_atom.x) - at_distance(at_gro.atoms[0].x)` — a **rigid single-molecule template**, offsets computed once relative to atom 1 and reused identically for every CG bead instance in the system, then added to that bead's own (generally non-ideal, e.g. a real equilibrated melt's) position. Extracting AT atoms from one molecule's *actual placement* inside an already-built hybrid captures that instance's positions *after* the idealized template got laid down against a non-ideal CG backbone — not the template itself. Feeding that back in as a new "template" and re-deriving relative offsets from it produces a *different, wrong* rigid shape, growing in error along the chain (confirmed empirically: atom-by-atom position drift increasing roughly linearly along the PE backbone, on the order of several Å by atom 8). The fix actually used: **convert `pe_single.gro`/`topol_aa.top` directly** into the LAMMPS `data`/`input_script` pair, via `backmap_prep`'s own `parse_gro`/`parse_top`/`units` functions (not extraction, not hand transcription) — this is what `examples/pe-lammps/` and `tasks.md` §5 now describe. `extract_at_frame.py` remains useful for its original purpose (a post-backmap AT-only production reference, e.g. `dodecane_at.data`), just not as a source for an AT-fragment *template*.
>
> This also invalidates the original dihedral-coverage plan in `tasks.md` §5.4 below ("use `examples/pe/`, which has dihedral params"): tracing `builder.py`'s intra-bead dihedral loop shows it additionally requires all 4 atoms of a dihedral to share one CG bead (`all_in_same`, `builder.py:598-601`). With 2-atom beads (every currently-existing linear-engine example, PE included), no 4-atom span is ever fully intra-bead — the `dihedral_coeff`/`ryckaert` code path is structurally unreachable regardless of which existing example is used, not merely uncovered by dodecane specifically. Real end-to-end coverage would need an example with a 3+-atom bead, which does not exist in this repository's linear-engine set today. Coverage for this path is unit/integration-level only (a synthetic fixture in `tests/test_lammps_data_parser.py`/`test_lammps_script_parser.py`), not example-level — documented as a known, structural limitation in `examples/pe-lammps/README.md` rather than silently left unmentioned.

## Goals / Non-Goals

**Goals:**
- Let a user supply an AT fragment as a LAMMPS `data` file (positions, per-atom type/charge/mass, bond/angle/dihedral connectivity by type ID) plus a bounded input-script fragment (`bond_coeff`/`angle_coeff`/`dihedral_coeff`/`pair_coeff` self-terms), instead of GROMACS `.gro`/`.top`.
- Adopt the numeric-atom-ID convention for `beads[].atoms` entries, consistent with the CG side's numeric-type-ID convention.
- Assume `units real`, no conversion — consistent with the CG-side change.
- Keep the existing GROMACS AT-fragment path, `builder.py`'s bead-mapping/placement logic, and the CG-system path (either format) completely unchanged.

**Non-Goals:**
- GROMACS `[virtual_sites3]`-equivalent support (e.g. explicit-hydrogen water models with a dummy interaction site) — no direct LAMMPS `data`-file construct maps onto it; a LAMMPS-native fragment needing virtual sites is out of scope for this change.
- Degree-dependent multi-file AT sources (`atoms_by_degree`, Phase 3 reactive-network bead mappings) — mirrors the CG-side change's linear-engine-only scope.
- Non-harmonic bonds/angles, non-RB dihedrals — the reader only needs to cover what `builder.py` actually consumes (see Context); anything else is already silently skipped on the GROMACS path too, so there's no regression in supporting the same subset here.
- OPLS-style combination-rule / forcefield.itp bundling — irrelevant to a LAMMPS-native reader (no combination-rule concept; see CG-side design.md precedent).

## Decisions

**Decision: `SourceFiles` gains `format`, `data`, `input_script` fields, mirroring `CGSystem`.** `format: lammps` requires `data`+`input_script`; `format: gromacs` (default) requires the existing `coordinates`+`topology`. Reject `format: lammps` combined with a `list[DegreeSourceFile]` source (degree-dependent) or `prep.engine: network`, at the same validation layer the CG-side change added for `cg_system.format: lammps` + network engine.
*Alternative considered*: reuse `cg_system`'s exact two-field shape (`data` only, no script) by requiring coefficients embedded in the `data` file's optional `Bond Coeffs`/`Angle Coeffs`/etc. sections. Rejected for the same reason the CG-side design rejected it: forces an unnatural file layout, and doesn't match how this project's own existing AT production input scripts (`in.dodecane_at`) already keep coefficients separate from the data file.

**Decision: the AT-fragment `data`-file reader reads `Bonds`/`Angles`/`Dihedrals`, unlike the CG reader.** This is the one structural difference from `parse_cg_system()`: those sections are load-bearing here (see Context), so they must be parsed into `TopBond`/`TopAngle`/`TopDihedral` objects with correct type IDs, atom-index references, and (from the paired input-script) resolved parameters.

**Decision: the input-script reader covers exactly four command families — `bond_coeff`, `angle_coeff`, `dihedral_coeff`, `pair_coeff` (diagonal only)** — no `units` enforcement command beyond requiring the literal declaration be `real` (same as the CG-side decision), no `hybrid` style combinations (AT fragments are always analytic in this codebase, never tabulated), no `pair_modify mix` (cross-terms are always Python-computed, never read). This is a smaller grammar than the CG-side design originally scoped, because AT-fragment force fields don't have the CG side's tabulated-potential complexity.
*Alternative considered*: reuse the CG-side change's full grammar (styles, `hybrid`, `pair_modify mix`, table passthrough) in case future systems need it. Rejected — YAGNI; nothing in `builder.py` would consume tabulated AT-fragment bonds/angles/dihedrals/pairs, so parsing them would produce data nothing can use, same principle the CG-side design applied when it dropped the input-script parser entirely.

**Decision: numeric LAMMPS atom ID as the `atoms:` entry identity, only for molecules whose `source.format: lammps`.** No schema-level cross-check ties `beads[].atoms` values to `source.format` (same as today: nothing validates that a GROMACS-format `atoms:` entry names a real atom until build time) — document the convention, and let a missing/invalid ID surface as the same "atom not found" condition the GROMACS path already produces for a bad name.

**Decision: AT-fragment atom-type strings are namespaced (`f"AT{type_id}"`), not bare numeric IDs.** Found while building `examples/pe-lammps/` (fully LAMMPS-native: both `cg_system` and `molecules[].source`): `build_system()` keys a single shared `type_map` dict by `atom.type` string across CG *and* AT atoms in the same build. `parse_cg_system` already uses bare numeric strings ("1", "2", ...) for CG types; if the AT-fragment reader used the same bare-numeric convention, a CG type "1" and an AT type "1" would collide and silently merge into one type whenever both sides use `format: lammps` with overlapping ID ranges — the common case, since both naturally start counting from 1. Prefixing AT-fragment type names (`AT1`, `AT2`, ...) makes collision structurally impossible, at no cost to the user (this string is never user-facing — `beads[].type`/`table_groups` only ever reference *CG* type names, and AT-fragment identity for the user is via `beads[].atoms` atom IDs, not type names).
*Alternative considered*: give `parse_cg_system` the namespaced convention instead (e.g. `CG1`, `CG2`) and leave AT-fragment types bare. Rejected — would have required revisiting and re-verifying the already-shipped, already-archived CG-side change instead of a purely-additive fix on the new code.

## Verification example

`examples/dodecane/extract_at_frame.py` already extracts a standalone AT-only `data` file (positions, `Bonds`, `Angles` with correct type IDs) from a backmapped hybrid output, and `in.dodecane_at` is already a hand-written input script in exactly the bounded shape this change needs. **This precedent turned out to be the wrong tool for building an AT-fragment template — see the "IMPORTANT CORRECTION" note in Context.** The verification example (`examples/pe-lammps/`, chosen over a dodecane variant specifically because PE's richer topology — angles, dihedrals, two AT atom types — exercises more of the reader even though the dihedral path specifically remains structurally unreachable, see the correction note) instead converts `pe_single.gro`/`topol_aa.top` directly via `backmap_prep`'s own parser/unit functions.

Verified: building `examples/pe/settings.yaml` and `examples/pe-lammps/settings.yaml` produces physically identical hybrid systems — all 1500 atoms match exactly on molecule ID, type, charge, and position; `in.pe`'s bond/angle/dihedral/pair coefficients match exactly (aside from the expected `.table` filename difference from the numeric-ID convention). The one residual difference is PBC image-flag (`ix iy iz`) bookkeeping for 79 of 1500 atoms — see the Risks entry below.

## Risks / Trade-offs

- **[Risk] A `data` file's `Bonds`/`Angles`/`Dihedrals` type IDs don't line up 1:1 with the input-script's `bond_coeff`/`angle_coeff`/`dihedral_coeff` IDs (e.g. a user hand-edits one file but not the other)** → Mitigation: validate at parse time that every type ID referenced in `Bonds`/`Angles`/`Dihedrals` has a corresponding coefficient entry in the input script; abort naming the missing type ID. Implemented and unit-tested.
- **[Risk] The dihedral code path (`dihedral_coeff`/`ryckaert` parsing) has no example-level integration coverage** → Confirmed structural, not fixable by picking a different existing example (see correction note): no linear-engine example maps a bead to 3+ atoms, so the intra-bead-dihedral condition (`all_in_same` across all 4 atoms) is never satisfied by any of them. Mitigation: unit/integration-level coverage via a synthetic fixture (`tests/test_lammps_data_parser.py`/`test_lammps_script_parser.py`) instead, and the limitation is disclosed in `examples/pe-lammps/README.md` rather than silently left to be discovered.
- **[Risk] PBC image-flag bookkeeping differs from the GROMACS path for atoms near a periodic boundary, even though positions are identical** → Root cause: `build_system()`'s post-build `prepare_network_coordinates()` call (`builder.py:1042-1044`) canonicalizes per-atom image flags by walking the bond graph in construction order; the LAMMPS-native AT-fragment reader's bond enumeration order differs slightly from the GROMACS `.top` parser's, changing which canonicalization the walk lands on for atoms whose molecule straddles a boundary. 0/1500 position/type/charge mismatches, 79/1500 image-flag-only mismatches, confirmed by direct atom-by-atom comparison.
  > **IMPORTANT CORRECTION (found running on real LAMMPS, after this change had already been archived and pushed):** this entry originally said "Verified benign" and "not treated as a defect to fix." That was wrong — it was asserted without actually running LAMMPS, on the (unverified) assumption that "positions match" implies "image flags are self-consistent." Running `examples/pe-lammps/` on LAMMPS (the project's compute VM) crashes within 2 steps with `WARNING: Inconsistent image flags` / `ERROR: Bond atoms ... missing`; direct calculation of unwrapped bond lengths (`x + ix*box`) confirms 34/1480 bonds have a genuinely inconsistent image-flag pair, not a benign relabeling. **Cross-checking a second, independent way** (per the project's debugging discipline — never let a surprising or convenient result stand unverified): running the *unmodified* `examples/pe/` GROMACS-path build on the same LAMMPS binary reproduces the identical failure (35/1480 bad bonds, same crash a few steps into the second `run` block). This confirms the bug is pre-existing in `network/pbc.py`'s `prepare_network_coordinates`/`_assign_image_flags_by_bond_tree`, not introduced or materially worsened by this change (34 vs 35 bad bonds) — it was simply never exercised by a full real-LAMMPS run of `examples/pe/` before this session. Left unfixed here (out of scope: pre-existing, unrelated to LAMMPS-native input, needs its own investigation); tracked separately per the user.
- **[Trade-off] Virtual-site AT fragments (e.g. explicit-hydrogen water models) can't use this path** → Explicitly disclosed as a non-goal rather than silently unsupported; GROMACS remains the only path for such fragments.
- **[Trade-off] Two new small parsers (data-file connectivity reader, input-script coefficient reader) instead of one** → Accepted; each is independently bounded and testable, and the split mirrors how this project's own examples already keep `data` and `.in` files separate.

## Open Questions

- Should the input-script reader tolerate (ignore) a `pair_coeff i j` cross-term line, or reject it as an unsupported construct? Leaning toward tolerate-and-ignore (matches `in.dodecane_at`, which already includes cross-terms the reader doesn't need) rather than forcing users to strip lines from a real production input script before reuse.
- Same `include` question the CG-side design raised and left open (single-level support vs. reject) — resolve identically here for consistency, whatever that turns out to be.
